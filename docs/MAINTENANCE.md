# 维护者经验手册（防屎山 · 防恶意代码）

面向**维护者**（我）。协作者该看的规则在 [`../CONTRIBUTING.md`](../CONTRIBUTING.md)，
PR 处理流程在 [`COLLABORATION.md`](COLLABORATION.md)。

> **这份文档的用途**：这个项目现在**由自动化持续改动**（外部 agent 提 PR、我合并且自己也在改）。
> 自动化没有"项目品味"——它只会让代码**越积越多**。这份文档是**唯一会拦它的东西**。
>
> **每次审计后往「教训库」里加条目。** 不写下来的教训等于没学到 ——
> 下一个 agent（或三个月后的我）会犯同样的错。

---

## 0. 三条铁律

```
① 宁可不合，不要合了再修 —— 回滚一个坏 PR 的成本 < 清理它留下的烂摊子的成本
② 任何"看起来只是小改动"都要过闸门 —— 本项目已发生多次"小改动造成大问题"
③ 写下来的教训才存在 —— 代码注释里写"为什么"，这份文档写"这类错误怎么防"
```

## 1. 什么【不该合并】（拒绝清单）

### 1.1 一次做多件事的 PR

```
❌ "顺手清理了一些死代码 + 修了这个 bug + 重构了那个函数"
✅ 一个 PR 只做一件逻辑上的事

理由：混合 PR 的 diff 无法被有效审查 —— 审查者会在"真正的那处改动"上分心。
      而回滚时会把好的改动一起回滚掉。
```

**例外**：清理死代码**单独成 PR**（那样它可以被快速审完并合）。

### 1.2 放宽任何风控的改动

```
❌ 调大 maxPositions / 杠杆上限 / maxMarginUsage / 名义价值上限
❌ 调小 minRiskRewardRatio / minConfidence
❌ 去掉 requireStopLoss
```

**这是绝对红线**（`AGENTS.md` §4.2）。哪怕测试全绿也不能合 ——
风控是这个系统唯一"物理上"能阻止亏钱的东西。

⚠️ **真实教训**：曾有 PR 为了让一个测试通过而调大 `minPositionSize`，
而那个参数与账户规模是**算术关系**（调大后小账户永远开不了仓）。

### 1.3 绕过风控引擎的新下单路径

```
❌ 任何新的 broker.placeOrder() 调用点（除非在 reviewOpen/reviewClose 之内）
❌ executeOpen/executeClose 里"因为模型说了 X 所以这次例外"的分支
```

**检查方法**：diff 里搜 `placeOrder` —— 它只该出现在
`risk/engine.ts` 的下游、`liveSmokeTest.ts`（人工确认过）、`emergencyFlatten`（减敞口）。

### 1.4 引入原生依赖

```
❌ better-sqlite3 / bcrypt / sharp / 任何需要 node-gyp 或预编译二进制的包
```

**理由**：`node:sqlite` 是刻意选的，为了让 `npm install` 没有编译步骤。
引入原生依赖会把这个优势抹掉，而且失败信息通常完全指不到原因。

**判断方法**：`git diff package.json` 里出现新的 `dependencies` 条目 → 必须问"为什么内置的做不到"。

### 1.5 站点专属信息

```
❌ 主机名、域名、IP、服务器路径、真实凭据
✅ 占位符：my-server / https://quant.example.com / /srv/<应用目录>
```

⚠️ CI 的密钥扫描只抓常见字面量，**抓不到"一个看起来无害的真实域名"** —— 这一条靠眼睛。

### 1.6 提交信息写成技术报告

```
❌ 一行标题 + 四十行"起因/决定/效果/验证/实测数字"
✅ 一行标题（"为什么"写在代码注释里）
```

**理由**：这个仓库会同步到 GitHub，提交历史对任何人可见。
技术报告式的提交信息会把工作过程与内部推理摊开，而且**没人会在 `git log` 里读它们**。

⚠️ **真实代价**：本仓库曾因此重写全部历史（231 个提交合计 20.9 万字符，最长一条 91 行）。

## 2. 什么【验证不够缜密】（退回清单）

### 2.1 "测试全绿"不等于"接线通了"

```
真实事故：某个改动让"模型的原生工具调用格式没被接住"——
         而它【不报错】，只是静默地少了一次调用（正在烧钱）
```

**判据**：改动涉及**外部系统**（币安响应字段、LLM 方言、端点形状）时，
必须在**真实环境**验证，或明确标注"未在真实环境验证"。

### 2.2 只跑了单元测试就声称"能用"

```
验证阶梯（AGENTS.md §6.1）：
  ① 单元测试 → ② npm run sim → ③ sim:live → ④ demo → ⑤ 实盘冒烟 → ⑥ 真实交易
  碰了下单路径的改动：至少到 ②
```

⚠️ **"我读过觉得对"不是验证**。

### 2.3 测试断言写的是"实现算出来的值"

```
❌ assert.equal(result, 我实现算出的数)
✅ assert.equal(result, 交易所真实响应里观测到的数)
```

**理由**：实现与参考值不一致时，**默认是实现在错**。
为了让测试通过而改断言，等于把 bug 固化下来。

### 2.4 新增行为没有测试

```
❌ "这个改动很小，不用测试"
✅ 修 bug 的测试必须在【修复前会失败】
```

### 2.5 声明"已完成"但没有部署验证

```
❌ 提交推送 = 做完了
✅ 提交 + 部署 + 回读线上 build-info.json 的 commitShort == 本地 HEAD
```

**没有部署的迭代等于没做完**（`AGENTS.md` §4.6）。

## 3. 屎山特征（定期扫描）

### 3.1 一次性报告留在 `docs/` 根目录

```
❌ AGENT-DELIVERY-STATUS.md / AGENT-RUNTIME-OBSERVATIONS.md / …
   （"第 3 轮观察后"、"部署记录" —— 这些是【当时的快照】，不是长期文档）

✅ 教训进代码注释；需要留档的判断进 docs/ 的正式文档；
   一次性记录进 docs/archive/
```

**判断方法**：
```
· 标题含"第 N 轮"、"当前状态"、"交付记录" → 一次性
· 被其它文档引用 0 次 → 孤岛
· 含过时事实（旧用例数、旧版本号、"待验证"） → 已腐烂
```

⚠️ **真实教训**：2026-10-14 审计发现 6 个这类文件（零引用、含过时事实），
它们是**我自己早期留下的工作汇报**。清理时归档而非删除（保历史可追溯）。

### 3.2 超大文件

```
当前 Top 8（2026-10-14）：
  10368  trader/autoTrader.ts      ← 最大，但它是既有架构
   4328  strategy/prompt.ts
   4004  store/repositories.ts
   3857  trader/manager.ts
   2852  web/components/DecisionFeed.tsx
```

**判断**：新增代码让某个文件**继续膨胀**时要问"这段逻辑属于这里吗"。
不要求立刻拆分（拆大文件的风险高于收益），但**不要让它更糟**。

### 3.3 死代码 / 注释掉的代码

```
❌ 大段被注释掉的实现（"以后可能用得上"）
❌ 导出但无人引用的函数
❌ 声明后从未使用的变量
```

**扫描**：`grep -rn "^\s*//\s*\(const\|let\|function\|export\|import\)"`

### 3.4 重复实现

```
❌ 同一个算术写在两个地方（"改一处等于没改"—— 本项目已踩过两次）
❌ 两个角色做同一件事（如 firm.ts 的 system_engineer 与已删除的 engineer）
```

⚠️ **真实教训**：曾同时存在 `engineer` 与 `system_engineer`（**中文名完全相同**），
而前者是孤儿（零调用点、未登记档位 → 静默回退 T2）。
**加角色前必须先查组织架构层**（`firm.ts` 的 `FIRM_ROLES`）。

## 4. 恶意代码特征（安全审计）

### 4.1 原型污染

```
真实案例（2026-10-14，外部贡献者发现）：
  set_params 的点号补丁可以经 __proto__ 污染全局原型
```

**扫描**：搜 `__proto__`、`constructor[`、`Object.assign(` 的**用户可控键**。

### 4.2 SSRF（服务端请求伪造）

```
真实案例：urlGuard 曾漏掉 OCI 元数据段与 SIIT/NAT64 隔离前缀
```

**扫描**：任何"用户可控 URL"的请求路径（`fetch` / `redirect`），
检查每一跳是否重跑校验、跨主机是否剥掉鉴权头。

### 4.3 凭据泄露

```
扫描新增行里的 api_secret / api_key / passphrase / private_key 字面量
（CI 已自动做这一条）
```

### 4.4 后门 / 数据外泄

```
❌ 把数据发往非预期的域名
❌ 在日志里打印凭据（只允许掩码 maskSecret()）
❌ 读取 .env / data/ 并外传
```

**扫描**：新增的 `fetch(` / `http` 调用点，逐个看目标域名是否在预期内。

## 5. 审计节奏

```
每次处理 PR 时：过 §1 + §2 的清单（那是闸门，见 COLLABORATION.md）
每周一次：跑 §3 的扫描（屎山特征）
每两周一次：跑 §4 的扫描（安全）
每次审计后：往 §6 教训库加条目
```

### 一键扫描命令

```powershell
# 屎山特征
grep -rn "TODO\|FIXME\|HACK" packages/*/src --include="*.ts" --include="*.tsx" | grep -v test
grep -rn "^\s*//\s*\(const\|let\|function\|export\|import\)" packages/*/src --include="*.ts"
git diff --stat HEAD~20 HEAD -- package.json          # 新增依赖？
Get-ChildItem packages/*/src -Recurse -Include *.ts,*.tsx |
  Where-Object { $_.Name -notmatch '\.test\.' } |
  ForEach-Object { [PSCustomObject]@{ L=(Get-Content $_.FullName).Count; N=$_.FullName } } |
  Sort-Object L -Descending | Select-Object -First 10

# 安全
grep -rn "__proto__\|constructor\[" packages/*/src --include="*.ts"
grep -rn "fetch(" packages/server/src --include="*.ts" | grep -v test

# 孤岛文档
Get-ChildItem docs -Filter "*.md" | ForEach-Object {
  $n = $_.Name
  $refs = (Select-String -Path docs/*.md,*.md -Pattern ([regex]::Escape($n)) -ErrorAction SilentlyContinue |
           Where-Object { $_.Filename -ne $n }).Count
  if ($refs -eq 0) { "孤岛: $n" }
}
```

## 6. 教训库

> 每条格式：**现象 → 根因 → 怎么防**。只写真实发生过的。

### L1 · 两个各自正确的决定合起来错了（组合性缺陷）

```
现象：#11 团队模式 87 轮零开仓。查材料发现前 6 个候选【全部】是 ai_requested。
根因：① strategy/coins.ts "ai_requested 先加 —— 顺序就是优先级"  ← 对
      ② tradingDesk "12 个候选会让模型只想不说，只取 6 个"        ← 对
      合起来：ai_requested 占满前 6 个 → 分析师永远只看那一类
怎么防：改动"取前 N 个"这类逻辑时，问"前 N 个是怎么排的"。
        两个决定单独看都对、合起来错，是这类 bug 的唯一形态。
```

### L2 · 用"典型值"设边界，而不是"最坏情况"

```
现象（三次，同一类）：
  · market_analyst 预算给 2048（典型值）→ 思维链一长 content=0 → 角色失败
  · technical 超时给 60 秒（前三次实测 8–12 秒）→ 第四次 54.3 秒就超
  · roleTimeoutMs 按"读一遍"估（10 秒/万字符）→ 真实要 80–130 秒/万字符
     → 裁决官每轮被切断，20 个候选只点评 5 个
根因：用乐观值设边界。
怎么防：边界用【实测最坏值 × 1.2】。留余量不是浪费 ——
        被切断的代价（决策不完整）远大于多等两分钟。
```

### L3 · 只在某模式下存在的东西，在别的模式产生了副作用

```
现象：#10（ai_managed）的决策区变成一片空白。
根因：我为团队模式把决策区压到 max-h-[10%]，而工作流区只在 ai_team 渲染
      → ai_managed 没有任何东西去填那 90%。
怎么防：改共用组件的样式/逻辑时，逐模式想一遍。
        判据："这个改动对另外两个模式意味着什么？"
```

### L4 · 状态与实现漂移（界面撒谎）

```
现象：汇报员显示"规划中"，但它已在跑（线上有运行日志）。
根因：tradingDesk.ts 接线了 reporter，但 firm.ts 的 status 没跟着改。
怎么防：接线一个岗位时【同时】改 firm.ts 的状态，并加测试钉住
        "staffed ⟺ 生产代码里有调用点"（firmStatus.test.ts 已做）。
```

### L5 · 材料自相矛盾（模型花力气解释矛盾而不干活）

```
现象：四个分析师每轮各写 200–400 字免责声明。
根因：材料标题说"候选 14 个，前 10 个完整"，而分析师只收到 6 个。
怎么防：裁剪材料时【同步改写标题】。材料的每一句都必须与它实际给的内容一致。
```

### L6 · 提示词里承诺了不存在的工具

```
现象：分析师每轮都写"我不能调用任何工具"。
根因：提示词说"你可以用 get_klines 点名要完整序列"，而团队角色【没有工具】。
怎么防：改提示词时问"这句话承诺的东西，它真的能拿到吗"。
```

### L7 · 系统的一句话压过了用户/策略师的规则

```
现象：#11 连续 40+ 轮零开仓，而策略师明文写"有 ≥0.8% 位移就必须开仓"。
根因：裁决官 task 里系统写着「如果双方证据都不足，'不行动'是正确答案」
      —— 那是一句【万能借口】，压过了策略师的所有规则。
      实测：BLUR +2.43% 触发，裁决官仍用"接飞刀"拒绝（策略师明文禁止的理由）。
怎么防：系统提示词里不要替智能体定"业务门槛"。
        要写就写"该听谁的"（门槛是策略师定的）。
```

### L8 · 一次性报告留在 docs/ 根目录 → 屎山

```
现象：docs/ 里有 6 个 AGENT-*.md（"第 3 轮观察后"、"部署记录"）。
根因：外部/早期的 agent 把"工作汇报"当成"项目文档"写进了仓库。
怎么防：见 §3.1 的判据（标题含"第 N 轮"/零引用/含过时事实）。
        一次性记录进 docs/archive/。
```

### L9 · "修复"引入了新回归

```
现象：我为了让团队模式的工作流占主导，把决策区压到 10%，
      结果 #10（ai_managed）空白（见 L3）。
根因：修复时只想着"目标场景"，没有想"其它场景"。
怎么防：修完一个 bug 后，问"这个改动还会影响谁"。
        既有测试若变红，先假设【我引入了回归】，而不是"测试过时了"。
```

### L10 · 同一个问题被两边独立发现（协作的正常形态，不是浪费）

```
现象：外部贡献者与我独立修了同一个 timeInForce 缺失（rebase 冲突）。
判断：这是【好事】—— 说明 CI 在报告问题、两边都在响应。
怎么防：冲突时合并两者的优点（他们的结构 + 我的注释），
        并在注释里记录"两边都抓到了"（说明这类错误容易犯）。
```

### L11 · "归档"与"删除"的取舍（清理屎山时的纪律）

```
现象：2026-10-14 审计发现 docs/ 有 20 个一次性文档（零引用、含过时事实）。
做法：**归档到 docs/archive/，不删除**。
理由：① 它们记录了"当时的判断"——包括【我判断错的时候】（如 FINDING-long-only-bias
         推翻了我上一轮的诊断），那类记录最有价值；
      ② 删掉会丢失"为什么当时那么做"的可追溯性；
      ③ 归档保留了历史，同时让 docs/ 根目录只剩【长期有效】的文档。
怎么防：清理时先分类（有教训价值 / 纯过程记录），再决定归档还是保留。
        一刀切删除会丢掉教训；一刀切保留就是屎山。
```

### L12 · 归档前必须确认无引用（否则断链）

```
现象：归档文档会断掉指向它的链接，而 CI 有 `npm run check:links`。
做法：归档前先 grep 全仓引用；归档后立刻跑 `npm run check:links`。
真实数据：本次归档 14 个文件后，52 个 md、119 个链接全部有效 ✅
怎么防：把"归档 → 跑链接检查"当成一个动作，不要分两次做。
```

### L13 · 维护者自己也会留下屎山（最容易被忽略的一条）

```
现象：docs/ 里那 6 个 AGENT-*.md 是【我自己】2026-09-17 留下的工作汇报。
根因：交付时把"工作汇报"当成了"项目文档"。
怎么防：写完一份文档前问一句"三个月后还有人读它吗"。
        没有 → 它属于对话记录或 docs/archive/，不属于 docs/ 根目录。
```

```
→ 但"没有发现问题"不等于"机制可以省" —— 本手册就是那套机制。
```
